# 死信队列 (DLQ) 治理实现

## 本次进展

- **重试上限校验**：在 `WorkerCallbackApplicationService` 中引入了重试上限校验逻辑。
    - 新增配置项 `ast.scheduler.callback.max-retry-count`，默认值为 3。
    - 当 Worker 上报失败且任务可重试时，系统会检查当前已重试次数。
- **死信状态流转**：
    - 如果重试次数超过上限，任务状态将不再流转至 `RETRY_WAIT`，而是直接进入 `DEAD_LETTER` 终端状态。
    - 确保护了系统资源不会被持续失败的任务无限占用。
- **集成测试验证**：新增了 `DeadLetterIntegrationTest`，验证了：
    - 达到上限后自动转入死信。
    - 未达上限时继续流转至重试等待状态。
- **可观测性增强**：在任务进入死信时，系统会打印一条 `WARN` 级别的日志，方便监控系统进行关键词告警。

## 当前状态

- 任务状态机闭环更加健壮，具备了基础的故障隔离能力。
- 死信任务保留在 MySQL 中，支持后续的人工介入或审计。

## 下一步建议

- **可观测性指标 (Prometheus)**：接入 Micrometer 暴露死信任务计数（DLQ Count）指标。
- **任务取消 API**：在网关侧实现任务的主动取消逻辑，同步清理调度队列。
- **Nacos Config 接入**：将 `max-retry-count` 等参数接入配置中心实现动态调整。
