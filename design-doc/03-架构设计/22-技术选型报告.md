# 平台整体架构技术选型

## 1. 文档目标

本文面向集团级异步任务调度中台，给出平台整体架构的技术选型结论、选型理由、边界约束与演进建议。

本文重点回答以下问题：

- 平台整体采用什么技术栈落地
- 各层组件分别解决什么问题
- 为什么当前阶段选择这些技术而不是其他方案
- 当前试点版与后续生产版的技术口径如何保持一致

## 2. 项目背景与选型原则

### 2.1 项目背景

当前平台要解决的问题不是“单一任务异步化”，而是“集团级、多业务、多任务类型、海量积压场景下的统一异步任务调度”。

项目已经明确以下关键约束：

- 核心隔离维度是 `tenantId + taskType`
- 当前阶段租户同权，不引入 VIP、配额、优先级等差异化治理
- 必须支持海量任务积压，且不能因热点组合键导致严重 `HOL`
- 接入、缓冲、调度、执行、回调、补偿必须分层解耦
- 平台要优先复用成熟基础设施，避免重型自研

### 2.2 选型原则

平台技术选型遵循以下原则：

1. **成熟优先**
   
   - 优先选用团队已有运维经验、集团内已有沉淀的基础设施

2. **解耦优先**
   
   - 接入、缓冲、调度、执行、通知、补偿分层设计，避免单组件职责膨胀

3. **最终一致性优先**
   
   - 允许重复，不允许静默丢失
   - 通过外盒、幂等、重试、补偿闭环保证任务最终完成

4. **公平调度优先**
   
   - 不能让热点组合键通过高频触发霸占调度器
   - 调度顺序必须由 `Dispatcher` 统一裁决

5. **资源感知优先**
   
   - 调度决策必须基于 Worker 的实时运行态，而不是静态配置

6. **低心智负担优先**
   
   - 当前阶段不引入独立注册中心、不引入复杂协调框架、不建设重型多租户策略引擎

## 3. 整体架构选型结论

### 3.1 架构总览

当前平台采用以下总体架构：

- 接入层：`Gateway`
- 一级缓冲层：`RocketMQ 标准版`
- 二级逻辑调度层：`Pump + Dispatcher + Redis`
- 事实存储层：`MySQL 8.0`
- 执行层：`Worker SDK + Worker Group`
- 回调与通知层：`Callback Service + Notify Dispatcher`
- 治理与运营层：`Admin`
- 可观测层：`Prometheus + Grafana + ELK / Loki`
- 部署底座：`Kubernetes`

一句话结论：

**平台采用“Java 技术栈 + RocketMQ 一级缓冲 + Redis 二级逻辑调度 + MySQL 事实存储 + Kubernetes 集群部署 + Prometheus 可观测”的务实型企业级架构。**

### 3.2 核心选型摘要

| 架构层       | 选型                     | 角色定位                                       |
| --------- | ---------------------- | ------------------------------------------ |
| 服务开发语言    | `Java`                 | 平台主开发语言                                    |
| 应用框架      | `Spring Boot`          | 承载 Gateway、Scheduler、Callback、Notify、Admin |
| 服务通信      | `HTTP + gRPC`          | 对外接入与内部高性能通信                               |
| 消息缓冲      | `RocketMQ 标准版`         | 一级削峰、海量堆积、Pump 消费入口                        |
| 关系型存储     | `MySQL 8.0`            | 任务事实源、状态机、外盒、审计与补偿基线                       |
| 调度缓存/状态视图 | `Redis Cluster`        | 二级逻辑队列、Worker 元数据与运行态                      |
| 监控告警      | `Prometheus + Grafana` | 指标采集、告警、容量分析                               |
| 日志检索      | `ELK / Loki`           | 日志检索、链路排障、审计辅助                             |
| 部署平台      | `Kubernetes`           | 无状态服务容器化、弹性扩缩容、灰度发布                        |

## 4. 分层技术选型

### 4.1 开发语言与应用框架

#### 选型结论

- 开发语言：`Java`
- 应用框架：`Spring Boot`

#### 适用组件

- `Gateway`
- `Pump`
- `Dispatcher`
- `Callback Service`
- `Notify Dispatcher`
- `Compensator`
- `Admin`

#### 选型理由

- Java 生态成熟，适合建设长期演进的基础平台
- 对并发编程、线程池治理、连接池治理、RPC 框架、中间件生态支持充分
- 团队对 `RocketMQ`、`Redis`、`MySQL` 的 Java 接入生态最成熟
- `Spring Boot` 适合快速构建统一的服务治理、配置管理、监控暴露与运维规范
- 适合沉淀统一的 `Worker SDK`、任务协议、幂等拦截、审计埋点与通用 starter

#### 设计约束

- 平台控制面优先统一在 Java 技术栈收敛，降低跨语言治理成本
- 业务 Worker 可保持多语言扩展能力，但平台控制面不建议首期多语言混建

### 4.2 接入协议与服务通信

#### 选型结论

- 对外接入协议：`HTTP`
- 内部高性能通信：`gRPC`
- 健康探测：`HTTP /health` 或 `gRPC health check`

#### 适用场景

- 上游业务系统提交任务
- Worker 注册与心跳上报
- 调度器向 Worker 派发任务
- 平台回调业务方结果通知

#### 选型理由

- `HTTP` 通用性强，适合大多数业务系统快速接入
- `gRPC` 更适合平台内部低延迟、高吞吐的派发链路
- 双协议并存可以同时兼顾“开放接入”与“平台内部性能”
- 与统一认证、签名、超时、重试、幂等协议更容易集成

#### 设计约束

- 首期对外接口以 `HTTP` 为主，降低业务方接入门槛
- 对性能敏感的 Worker 派发与回调场景优先支持 `gRPC`
- 不建议在首期同时支持过多通信协议，避免测试矩阵膨胀

### 4.3 消息缓冲层

#### 选型结论

- 消息中间件：`RocketMQ 标准版`

#### 角色定位

- 新任务主入口缓冲
- 高峰流量削峰填谷
- 海量任务堆积承载层
- `Pump` 的阻塞消费来源

#### 选型理由

- 适合高吞吐、可堆积、可靠投递的异步任务入口场景
- 团队通常已有成熟的 `RocketMQ` 运维与治理经验
- 支持延迟消息、消费组、重试等基础能力，适合作为一级缓冲层
- 可以把接入压力与调度压力拆开，避免任务提交链路直接打到调度内核

#### 为什么不是 RocketMQ 直接消费即派发

- RocketMQ 物理队列适合缓冲，不适合直接承担高基数 `tenantId + taskType` 公平调度
- 若直接消费即派发，热点任务容易在 MQ 物理层产生明显 `HOL`
- 当前项目强调公平调度与资源感知，因此必须引入 Redis 二级逻辑调度层

#### 当前阶段不采用项

- 不采用 `RocketMQ 5.x LiteTopic`
  - 原因：当前基础设施约束下不可直接依赖
- 不采用“MQ 直接做最终公平调度”
  - 原因：无法满足当前项目对全局公平裁决和热点治理的要求

### 4.4 二级逻辑调度与状态缓存层

#### 选型结论

- 缓存与调度状态层：`Redis Cluster`

#### 角色定位

- 维护二级逻辑调度队列
- 维护全局活跃组合键集合
- 维护 Worker 注册元数据与最新运行态
- 作为 Dispatcher 高频读取的实时状态视图

#### 选型理由

- 读写性能高，适合承担高频就绪队列、执行态和运行态快照
- 适合通过 List、ZSet、Set 等结构实现 `ready / processing / retry / active keys`
- 支持 Lua 原子脚本，便于实现“ready 出队 + processing 入队”的原子领取
- 适合作为 Worker 运行态聚合视图，供 Dispatcher 高频读取

#### 当前方案中的关键定位

Redis 不是任务事实库，而是：

- 二级逻辑调度层
- 短期执行态缓存
- Worker 最新状态视图

关键 Key 示例：

- `dispatch:ready:{tenantId}:{taskType}`
- `dispatch:processing:{tenantId}:{taskType}`
- `dispatch:retry:{tenantId}:{taskType}`
- `dispatch:active:keys`
- `ats:worker:group:{workerGroup}`
- `ats:worker:meta:{workerId}`
- `ats:worker:runtime:{workerId}`

#### 为什么不是纯 Redis 方案

- 纯 Redis 持久化不适合作为任务事实源
- 审计、状态追溯、补偿对账、终态闭环仍需要关系型数据库承接
- 平台需要的是“Redis 做高频运行态，MySQL 做最终事实源”的分层模型

### 4.5 事实存储与状态基线

#### 选型结论

- 关系型数据库：`MySQL 8.0`
- 后续扩展候选：`TiDB`

#### 角色定位

- 任务事实表
- 状态机流转
- 入队外盒表
- 业务回调外盒表
- 审计日志与补偿对账基线
- 死信、失败原因与重试轨迹沉淀

#### 选型理由

- 事务能力稳定，适合承接任务事实与状态机更新
- 适合通过索引、分页、归档等常规手段支撑任务查询与运营检索
- 便于实现外盒模式，确保“落库成功”和“异步动作可补偿”之间的最终一致性
- 适合作为平台的最终事实源、补偿源和对账源

#### 为什么不是纯数据库轮询调度

- 高并发场景下轮询成本高
- 容易把数据库拖成热点系统
- 不适合承接高频调度竞争与 Worker 实时状态

#### 演进建议

- 首期以 `MySQL 8.0` 为主
- 当任务规模、历史归档、跨分片扩展压力明显提升时，再评估引入 `TiDB`

### 4.6 调度器实现模式

#### 选型结论

- 调度内核采用 `Pump + Dispatcher` 双层模型

#### 职责拆分

- `Pump`
  
  - 从 `RocketMQ` 阻塞消费
  - 快速搬运到 `Redis` 二级 ready queue
  - 激活组合键并唤醒 Dispatcher

- `Dispatcher`
  
  - 常驻调度循环
  - 基于全局 active keys 做公平裁决
  - 基于 Worker 实时运行态做资源感知派发

#### 选型理由

- 把“搬运”和“派发”拆开，避免热点流量直接挤占公平调度资源
- 让 MQ 专注缓冲，Redis 专注逻辑调度，Dispatcher 专注公平裁决
- 更适合落地 `Round Robin -> DRR` 的渐进式演进路线

#### 为什么不是单体 Scheduler

- 单体 Scheduler 同时负责 MQ 消费、状态视图、派发裁决、资源判断时，职责过重
- 在热点任务、高并发和多来源唤醒场景下，容易出现触发与派发耦合
- 当前项目明确要求“触发只负责唤醒，派发顺序由 Dispatcher 统一裁决”

### 4.7 Worker 管理与注册发现

#### 选型结论

- 当前阶段不引入独立注册中心
- 采用“平台注册接口 + Redis 最新运行态 + Prometheus 历史指标”的轻量模式

#### 角色定位

- Worker 启动时直连平台注册
- Worker 周期性上报心跳、负载和并发槽位
- 平台将最新运行态写入 Redis
- Dispatcher 基于 Redis 中的状态视图完成选点

#### 选型理由

- 当前目标只是“被平台发现、被调度器读取、被运维看见”，无需上升到独立注册中心
- 相比引入 `Nacos` 等组件，控制面更轻、接入链路更短、实现周期更短
- 当前 Worker 状态重点是“最新快照”，不是复杂服务治理

#### 当前阶段不采用项

- 不引入 `Nacos`
  - 原因：当前项目不需要重型注册发现与配置中心能力
- 不把 Worker 历史状态写 MySQL
  - 原因：历史趋势更适合交给 Prometheus

### 4.8 可观测体系

#### 选型结论

- 指标监控：`Prometheus + Grafana`
- 日志检索：`ELK / Loki`

#### 角色定位

- 采集平台服务指标、任务指标、Worker 指标、中间件指标
- 支撑告警、容量分析、压测评估与故障排查
- 沉淀任务链路、失败原因、异常波动、回调失败等观测信息

#### 选型理由

- `Prometheus` 适合保存高频时序指标
- `Grafana` 适合统一看板、报表与告警联动
- `ELK / Loki` 适合检索链路日志、错误日志与审计辅助信息
- 与 Kubernetes、Java 服务、中间件生态集成成熟

#### 指标分工原则

- Redis：保存最新运行态
- Prometheus：保存历史时序指标
- MySQL：保存任务事实、终态和审计基线

### 4.9 部署与运行底座

#### 选型结论

- 容器编排平台：`Kubernetes`

#### 适用组件

- `Gateway`
- `Pump`
- `Dispatcher`
- `Callback Service`
- `Notify Dispatcher`
- `Compensator`
- `Admin`

#### 选型理由

- 平台各控制面服务均是无状态或弱状态服务，适合容器化部署
- 便于水平扩缩容、滚动发布、灰度发布和多可用区部署
- 与 Prometheus、日志系统、配置注入、资源限制等运维能力天然协同

#### 部署口径

- 单机试点版：控制面可收敛在单台 `4C8G` 环境，RocketMQ、Redis、MySQL 优先复用现有基础设施
- 集群生产版：控制面服务至少 `3` 实例，状态组件采用高可用集群

## 6. 当前不采用的技术方案

### 6.1 不采用 RocketMQ 5.x LiteTopic

原因：

- 当前基础设施与实施约束下不可直接依赖
- 平台必须基于 `RocketMQ 标准版` 先完成一版稳定落地
- 因此当前通过 `RocketMQ 一级缓冲 + Redis 二级逻辑调度` 解决高基数调度问题

### 6.2 不采用 MQ 直接消费即派发

原因：

- 无法充分解决 `tenantId + taskType` 高基数公平调度问题
- 热点任务容易在 MQ 物理队列层形成 `HOL`
- 不利于实现统一的全局 active keys 公平裁决

### 6.3 不采用纯数据库轮询调度

原因：

- 高并发下数据库轮询成本过高
- 不适合作为高频就绪队列和实时运行态载体
- 易把事实库拖成热点瓶颈

### 6.4 不采用纯 Redis 事实存储

原因：

- 审计、终态、补偿、回调闭环都需要稳定的事实源
- Redis 更适合高频运行态和调度态，不适合长期事实存储

### 6.5 不采用独立注册中心

原因：

- 当前 Worker 管理需求较轻
- Redis 最新快照 + Prometheus 历史趋势已经足够支撑调度与运维
- 额外引入注册中心会增加控制面复杂度和实施成本

## 7. 分阶段选型建议

### 7.1 P0：试点版

建议采用最务实组合：

- `Java + Spring Boot`
- `HTTP` 为主，`gRPC` 按需接入
- `RocketMQ 标准版`
- `Redis Cluster`
- `MySQL 8.0`
- `Prometheus + Grafana`
- `Kubernetes` 或等价容器运行环境

目标：

- 优先验证任务接入、二级调度、Worker 选点、回调闭环、补偿恢复

### 7.2 P1：生产版

继续增强：

- 完善 `gRPC` 内部派发链路
- 完善 Worker SDK 统一协议
- 完善日志平台、审计平台与告警规则
- 完善灰度发布、容量治理、热点治理和压测体系

### 7.3 P2：规模化演进版

按规模再评估：

- `TiDB` 是否替代或承接部分 MySQL 压力
- 更细粒度的 Worker 分池与资源标签体系
- 更强的公平调度算法，如 `DRR`
- 在基础设施允许时评估 `LiteTopic` 简化调度架构

## 8. 最终结论

在当前项目约束下，平台整体架构最合适的技术选型不是追求“组件最少”，而是追求“职责清晰、边界稳定、工程可落地、后续可演进”。

因此当前推荐的标准组合是：

**`Java + Spring Boot + HTTP/gRPC + RocketMQ 标准版 + Redis Cluster + MySQL 8.0 + Prometheus/Grafana + ELK/Loki + Kubernetes`**

这套选型能够满足以下目标：

- 支撑 `tenantId + taskType` 维度的逻辑隔离与公平调度
- 通过 `Pump + Dispatcher` 解耦 MQ 搬运与公平派发
- 通过 `Redis` 承接二级逻辑调度与 Worker 最新运行态
- 通过 `MySQL` 承接任务事实源、外盒、审计与补偿基线
- 通过 `Prometheus` 与日志系统形成完整可观测闭环
- 通过 `Kubernetes` 支撑集群化部署、弹性伸缩与灰度演进

一句话总结：

**当前平台的技术选型是一个面向企业生产环境的务实型组合，其核心不是单点技术先进性，而是围绕“可靠接入、可控调度、资源感知、最终一致性、可观测闭环”形成整体协同。**
