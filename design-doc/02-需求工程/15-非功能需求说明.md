# 非功能需求说明（NFR）

## 1. 适用范围与资源约束

本文档同时定义两套非功能目标：

- **单台 `4C8G` 试点版**
  - 用于 MVP、PoC、试点上线或小规模验证
- **集群生产版**
  - 用于多实例、多可用区、标准生产部署

默认假设如下：

- 控制面服务包括：`Gateway`、`Pump`、`Dispatcher`、`Callback Service`、`Notify Dispatcher`、`Compensator`
- `Worker` 作为独立执行节点，不与平台控制面强制同机部署
- `MySQL`、`RocketMQ`、`Redis` 优先复用现有基础设施
- 若 `MySQL`、`RocketMQ`、`Redis` 与控制面同机，则单机版指标需进一步下调 `30% ~ 50%`

### 1.1 两套目标的适用边界

| 维度    | 单台 4C8G 试点版 | 集群生产版        |
| ----- | ----------- | ------------ |
| 使用目的  | MVP、试点、压测验证 | 正式生产、集团推广    |
| 控制面部署 | 单机或单实例      | 多实例、Multi-AZ |
| 可用性目标 | 快速恢复、不丢任务   | 无单点、自动接管     |
| 验收重点  | 主链路跑通、异常闭环  | 稳定性、容量、SLA   |

### 1.2 典型部署假设

- **单台 4C8G 试点版**
  
  - 单台 `4C8G` 承担平台控制面
  - RocketMQ、Redis、MySQL 优先复用现有基础设施
  - 若中间件同机，需进一步下调性能指标

- **集群生产版**
  
  - Gateway、Pump、Dispatcher、Callback Service、Notify Dispatcher、Compensator 多实例部署
  - RocketMQ、Redis、MySQL 采用高可用集群
  - Worker 按 `workerGroup` 独立扩缩容

## 2. 性能要求

### 2.1 接入性能

| 指标         | 单台 4C8G 试点版                | 集群生产版                     |
| ---------- | -------------------------- | ------------------------- |
| 任务接收 TPS   | `300 ~ 800`                | `5000 ~ 20000`            |
| 峰值瞬时接收 TPS | `1000 ~ 1500`              | `20000 ~ 50000`           |
| 接口响应时间     | `P50 < 30ms`，`P95 < 100ms` | `P50 < 20ms`，`P95 < 80ms` |

### 2.2 调度性能

| 指标                         | 单台 4C8G 试点版                  | 集群生产版                      |
| -------------------------- | ---------------------------- | -------------------------- |
| 调度分发 TPS                   | `100 ~ 300`                  | `2000 ~ 8000`              |
| RocketMQ -> Redis 单轮搬运规模   | `20 ~ 100`                   | `50 ~ 200`                 |
| Redis -> Dispatcher 单轮领取规模 | `10 ~ 50`                    | `20 ~ 100`                 |
| 提交到 Worker 接收延迟            | `P50 < 200ms`，`P95 < 1000ms` | `P50 < 80ms`，`P95 < 300ms` |

### 2.3 回调性能

| 指标               | 单台 4C8G 试点版   | 集群生产版         |
| ---------------- | ------------- | ------------- |
| Worker 回平台回调处理耗时 | `P95 < 100ms` | `P95 < 50ms`  |
| 平台回调业务方          | 异步外盒，不纳入主链路承诺 | 异步外盒，不纳入主链路承诺 |

### 2.4 性能边界说明

- 单台 `4C8G` 试点版不应承诺集团终局指标。
- 集群生产版指标必须建立在多实例控制面、独立中间件集群和充分压测基础上。
- 若集群版控制面实例数低于 `3`，建议按表中指标的 `50% ~ 70%` 作为初始承诺值。

## 3. 并发要求

### 3.1 并发容量建议

| 指标                                 | 单台 4C8G 试点版         | 集群生产版                       |
| ---------------------------------- | ------------------- | --------------------------- |
| Worker Group 数量                    | `10 ~ 30`           | `50 ~ 200`                  |
| 活跃组合键数量                            | `100 ~ 500`         | `1000 ~ 10000`              |
| 二级 ready / processing / retry 任务总量 | 按 Redis 内存与压测结果动态校准 | 按 Redis Cluster 容量与分片规划动态校准 |
| 并发接入业务系统数量                         | `10 ~ 30`           | `50 ~ 200+`                 |

### 3.2 并发控制建议

- Gateway 线程池和连接池必须限流
- Pump 与 Dispatcher 必须分线程池隔离
- 平台回调业务方必须异步化，避免阻塞调度主链路
- 单组合键必须有单轮配额与并发上限，防止热点任务独占资源
- 集群生产版必须支持按 `workerGroup`、`tenantId + taskType` 维度独立限流和降级

## 4. 可用性要求

### 4.1 单台 4C8G 试点版目标

在单台 `4C8G` 服务器部署约束下，**不应承诺 `99.99%` 平台整体 SLA**。

当前阶段可接受目标应调整为：

- 单机版本目标可用性：`99.0% ~ 99.5%`
- 允许通过进程自动拉起、容器重启、外盒补偿实现故障恢复
- 单机故障会导致短时服务中断，但不得造成任务静默丢失

### 4.2 集群生产版目标

- 平台整体 SLA 目标：`99.95% ~ 99.99%`
- 任一单实例宕机不得造成整体服务不可用
- 任一控制面实例宕机应在秒级完成流量转移或消费接管
- 任务不因单点故障静默丢失

### 4.3 可用性边界说明

单机环境下无法满足以下生产级目标：

- 任一单节点宕机后整体无感知接管
- 跨实例无缝切流
- 真正意义上的无单点

因此当前阶段的可用性重点应放在：

- 快速恢复
- 状态可追踪
- 任务不丢失
- 补偿链路闭环

## 5. 可靠性要求

- 任务提交成功后至少执行一次
- 任务状态、业务回调与补偿链路必须可追踪
- 关键异常场景具备自动恢复能力
- Worker 回调失败、业务方回调失败、入队失败都必须有补偿机制
- 调度链路允许短暂重复，不允许静默丢失

### 5.1 重点保障机制

- MySQL 任务事实表
- 入队外盒与重发表
- RocketMQ 一级缓冲
- Redis 二级 ready / processing / retry 队列
- 超时扫描与补偿回灌
- 业务回调外盒与死信

## 6. 安全要求

- 接口鉴权
- 回调签名校验
- 审计日志留存
- 敏感数据脱敏
- 平台内部接口应限制来源 IP 或通过服务鉴权控制访问

## 7. 可扩展性要求

- 支持新增任务类型与 Worker Group
- 支持后续从单机控制面平滑扩展到多实例控制面
- 支持后续从单机试点升级为多 AZ 集群部署
- 支持后续接入 DAG、租户治理等能力

### 7.1 当前阶段扩展原则

- 优先保证模块边界清晰，而不是一次性堆满功能
- `Pump`、`Dispatcher`、`Callback Service`、`Notify Dispatcher` 应在部署层面可独立拆分
- Redis Key、RocketMQ Topic/Queue、MySQL 表结构需保留集群化扩展空间

## 8. 运维与观测要求

- 必须接入 Prometheus 指标采集
- 必须接入基础日志检索与 TraceID 关联能力
- 必须具备以下核心监控：
  - Gateway 请求量、错误率、限流量
  - RocketMQ 堆积深度、消费速率
  - Redis ready / processing / retry 队列长度
  - Dispatcher 派发成功率、派发延迟
  - Worker 心跳成功率、可用实例数、`availableSlots`
  - Callback / Notify 成功率、重试次数、死信量

### 8.1 告警要求

- RocketMQ 堆积持续升高
- Redis 队列积压超过阈值
- Worker 心跳中断
- Dispatcher 派发成功率下降
- Callback / Notify 死信异常上涨
- MySQL 连接池或慢 SQL 异常

### 8.2 不同阶段的监控重点

- **单台 4C8G 试点版**
  
  - CPU、内存、线程池、GC
  - RocketMQ 堆积与消费速率
  - Redis ready / processing / retry 长度
  - Dispatcher 派发成功率与回调成功率

- **集群生产版**
  
  - 所有单机版监控项
  - 各控制面实例负载均衡情况
  - Pump Consumer Group 消费漂移
  - Dispatcher 各实例派发分布
  - 多实例故障切换与跨可用区链路延迟

## 9. 兼容性要求

- 支持 Java/Go/Python SDK
- 支持 HTTP/gRPC 协议
- 支持不同业务系统使用统一任务协议接入

## 10. 压测与验收建议

### 10.1 单台 4C8G 试点版验收建议

- 使用 `3 ~ 5` 类典型任务类型进行混合压测
- 验证 `300 ~ 800 TPS` 接入能力
- 验证 `100 ~ 300 TPS` 稳定派发能力
- 验证任务积压、重试、超时、回调失败等核心异常场景
- 验证单机重启后外盒补发、补偿回灌和任务追踪链路可恢复

### 10.2 集群生产版验收建议

- 使用不少于 `5 ~ 10` 类典型任务类型进行混合压测
- 验证 `5000 ~ 20000 TPS` 接入能力
- 验证 `2000 ~ 8000 TPS` 稳定派发能力
- 验证多实例 Pump / Dispatcher 消费与派发分布均衡
- 验证单实例故障、MQ 堆积、Redis 队列积压、Worker 大面积异常等场景
- 验证多实例部署下的补偿闭环、死信处理和回调可靠性
