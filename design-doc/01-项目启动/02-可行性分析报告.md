# 可行性分析报告

## 1. 分析目标
评估集团级通用异步任务调度中台的业务可行性、技术可行性、成本可行性与实施风险。

## 2. 业务可行性
### 2.1 业务价值
- 统一异步任务接入方式，提升集团研发标准化水平。
- 将异步任务从业务系统剥离，减少业务系统复杂度。
- 支持对任务全生命周期进行可视化跟踪与人工干预。

### 2.2 业务适配性
适配的典型场景包括：
- 大批量导出
- 对账单生成
- 音视频转码
- AI 推理
- 自动化流程执行
- 通知下发与异步业务处理

## 3. 技术可行性
### 3.1 可行性结论
技术上可行，原因如下：
- 接入层可基于 HTTP/gRPC 实现语言无关接入。
- RocketMQ 可承载高吞吐缓冲与削峰。
- MySQL/TiDB 可承接任务事实存储与状态流转。
- Redis 可承接 Worker 状态、缓存与协调信息。
- Scheduler 与 Gateway 可无状态扩展。

### 3.2 技术难点
- 任务状态机设计与补偿闭环
- Worker 资源感知与调度路由
- 超时扫描与故障恢复
- 平台回调业务方的可靠通知
- 高吞吐场景下的压测与容量治理

## 4. 成本可行性
### 4.1 人力成本
建议核心团队至少包括：
- 架构/技术负责人 1 人
- 后端开发 2-4 人
- 测试 1-2 人
- 运维/平台支持 1 人

### 4.2 基础设施成本
- RocketMQ 集群
- Redis Cluster
- MySQL 或 TiDB
- K8s 集群资源
- Prometheus / Grafana / 日志系统

### 4.3 成本收益结论
虽然需要投入基础设施与平台研发成本，但长期收益显著高于重复建设成本。

## 5. 风险分析
- 架构复杂度上升，实施初期存在学习成本。
- 若状态机与补偿链路设计不严谨，容易出现任务不一致。
- 业务方接入标准不统一，可能拉长推广周期。
- 高并发压测不足会影响上线稳定性。

## 6. 风险应对建议
- 先做 MVP，先覆盖核心任务模型与核心业务场景。
- 建立统一的任务协议、回调协议与接入规范。
- 在灰度阶段选择 1-2 个核心业务双跑验证。
- 强化压测、混沌测试与故障演练。

## 7. 结论
项目具备明确业务价值、清晰技术路径与合理成本收益比，建议立项推进。
